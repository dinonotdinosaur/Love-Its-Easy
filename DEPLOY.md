# DEPLOY.md — обязательно перед деплоем

Чеклист того, без чего production-запуск **нельзя** считать готовым. Каждый
пункт закрывает конкретную дыру в безопасности или работоспособности —
причина указана рядом. Пополнять по мере появления новых требований.

## 0. Установка и запуск на сервере

- [ ] Node.js `^20.19 || ^22.12 || >=24.0` (поле `engines` в `package.json` —
      это пересечение требований Next.js 16 и Prisma 7).
- [ ] Зависимости — **`npm ci` без `--omit=dev`**. Prisma-клиент не хранится
      в репозитории, он генерируется при установке (`postinstall` →
      `prisma generate`), а `prisma`, `dotenv`, TypeScript и Tailwind — в
      devDependencies и нужны для `migrate deploy` и `next build`. С
      `--omit=dev` установка падает (проверено).
- [ ] Порядок: `npm ci` → `npx prisma migrate deploy` → `npm run build` →
      `npm start -- -H 127.0.0.1 -p 3000`.
- [ ] Запуск под systemd/pm2 с перезапуском при падении. При старте в
      production приложение проверяет обязательные переменные окружения
      (`lib/env-check.ts`) и при ошибке **завершается с кодом 1** с
      понятным сообщением в логе — это нормальное поведение, а не сбой.

## 1. Reverse proxy перед приложением

- [ ] Next.js слушает только локальный интерфейс (`next start -H 127.0.0.1`),
      порт приложения **не открыт наружу** — снаружи доступен только прокси.
- [ ] Прокси (nginx) выставляет `X-Forwarded-For` через
      `$proxy_add_x_forwarded_for`.

      **Почему:** лимит загрузок фото (`/api/upload`) считает запросы по IP
      клиента, а IP берётся из **последнего** адреса `X-Forwarded-For`
      (`getClientIp` в `lib/http.ts`) — его дописывает наш прокси, всё левее
      клиент может подставить сам. Без прокси (или если до приложения можно
      достучаться напрямую) клиент подделывает заголовок и обходит лимит.
- [ ] `client_max_body_size 16m;` — у nginx по умолчанию 1 МБ, а приложение
      принимает фото до 15 МБ. Без этого загрузка обычного фото с телефона
      будет падать на прокси с 413.
- [ ] HTTPS. PIN-cookie в production ставится с флагом `secure` и по HTTP
      не сохранится — вход по PIN не будет работать.

Пример конфигурации:

```nginx
server {
    listen 443 ssl;
    server_name loveitseasy.ru;
    client_max_body_size 16m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

- [ ] Приложение запущено **одним процессом**. Счётчик лимита загрузок
      (`lib/rate-limit.ts`) хранится в памяти процесса — при нескольких
      инстансах у каждого свой счётчик и лимит фактически умножается
      (см. AGENTS.md §2, масштабирование).

## 2. Переменные окружения

- [ ] Заданы все переменные из `.env.example`. Обязательные проверяются при
      старте — без них сервер не запустится (см. §0); `PAYMENT_*` и
      `UNISENDER_API_KEY` пока не используются кодом.
- [ ] `NODE_ENV=production` — выключает `/api/dev/complete-payment`
      (заглушка оплаты: переводит в PAID любой прошедший модерацию заказ без денег) и включает
      `secure` у cookie.
- [ ] `PIN_COOKIE_SECRET` и `CRON_SECRET` — длинные случайные строки
      (например `openssl rand -hex 32`), не значения из локального `.env`.
      Короче 32 символов — сервер не запустится.
- [ ] `S3_ENDPOINT` — **публичный** адрес хранилища, доступный из браузера,
      а не внутренний адрес в сети провайдера: из него строятся подписанные
      ссылки на фото, которые открывает браузер получателя квеста.

## 3. База данных

- [ ] `npx prisma migrate deploy` — применить все миграции из
      `prisma/migrations`.

## 4. Cron: очистка неиспользованных фото

Фото загружаются в S3 до создания заказа, брошенные формы оставляют файлы,
на которые не ссылается ни один заказ. Их удаляет
`POST /api/cron/cleanup-photos` (фото старше суток без ссылок из заказов).

- [ ] Первый запуск — вручную с `?dryRun=1`, проверить список `wouldDelete`.
- [ ] Ежедневный запуск в crontab на VPS:

```cron
0 4 * * * curl -fsS -X POST -H "Authorization: Bearer <CRON_SECRET>" http://127.0.0.1:3000/api/cron/cleanup-photos
```

При масштабировании — заменить на lifecycle-правило S3 (см. AGENTS.md §2).

## 5. Проверить на VPS до запуска (локально не проверяется)

Всё остальное проверено локально на production-сборке (`npm run build` +
`next start`): миграции на пустой базе, закрытая dev-оплата, `noindex` и
запрет кэширования на `/q` и `/demo`, `Secure`/`HttpOnly` у PIN-cookie,
загрузка фото ~13 МБ, cron-очистка, отказ старта без переменных. Эти пункты
зависят от сети и сервисов самого VPS:

- [ ] **OpenAI Moderation доступен с VPS.** OpenAI не обслуживает Россию —
      с российского IP API, вероятно, ответит 403 `unsupported_country`,
      и модерация текстов перестанет работать (заказы не будут проходить):
      ```sh
      curl -sS https://api.openai.com/v1/moderations \
        -H "Authorization: Bearer $OPENAI_API_KEY" -H "Content-Type: application/json" \
        -d '{"input":"test"}'
      ```
      Если не отвечает `200` с `results` — это вопрос к решению из AGENTS.md
      §2 (модерация текстов), а не к настройке сервера.
- [ ] **Postgres:** `npx prisma migrate status` проходит с продовым
      `DATABASE_URL`. Managed-Postgres обычно требует SSL (`?sslmode=...`,
      иногда CA-сертификат провайдера).
- [ ] **NudeNet:** `curl $NUDENET_SERVICE_URL/health` с VPS отвечает `ok`.
- [ ] **S3 провайдера:** один раз загрузить фото через форму заказа и открыть
      его на `/q/[uuid]` — проверяет ключи, бакет, path-style адресацию
      (`forcePathStyle` в `lib/storage/s3.ts`) и публичность `S3_ENDPOINT`.
- [ ] **Сквозной заказ** от формы до страницы квеста (после выбора
      платёжного провайдера — с реальной оплатой).
