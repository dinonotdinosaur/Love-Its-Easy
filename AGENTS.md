# AGENTS.md — loveitseasy

Этот файл — инструкция для AI-агентов (и людей), работающих в этом репозитории.
Источник истины по продукту — `love_its_easy.md` (ТЗ). Этот файл описывает,
**как** реализовывать ТЗ технически, и фиксирует решения, принятые поверх ТЗ
по итогам обсуждения слабых мест (архитектура, юнит-экономика, юридические
риски).

Код в репозитории пока отсутствует — это стартовая точка. Обновляй этот файл
по мере появления реальной структуры проекта (реальные пути вместо
предполагаемых, реальные команды вместо предполагаемых).

## 1. Суть продукта (кратко)

Микро-SaaS: пользователь выбирает шаблон квеста/сюрприза → заполняет поля
(без визуального конструктора) → материалы проходят автоматическую модерацию
→ оплата → пользователь получает неиндексируемую UUID-ссылку (опционально
защищённую PIN-кодом) на готовый сайт. Разовые платежи, без подписок.

## 2. Технологический стек

- **Frontend / витрина / рендер шаблонов**: Next.js (актуальная версия на
  момент инициализации — 16.x), App Router, TypeScript strict. Версия
  фиксируется на момент `next init`, дальше обновляется осознанно, а не
  автоматически — не путать "актуальная" с "всегда последняя без проверки".
- **Стили**: Tailwind CSS.
- **Анимации**: Framer Motion. Three.js — только для конкретных шаблонов
  (например «Признание в любви»), подключается через `dynamic import`
  (не в общий бандл), с обязательным фолбэком на CSS/Framer Motion при
  `prefers-reduced-motion` или отсутствии/слабой поддержке WebGL —
  продукт Mobile First, 3D не должно ломать перформанс на бюджетных телефонах.
- **Backend**: Next.js API Routes (без отдельного Node-сервера, пока не
  появится причина его завести).
- **БД**: Managed PostgreSQL у российского провайдера (Timeweb Cloud или
  Yandex Cloud). **Персональные данные и загруженные фото не должны покидать
  RU-юрисдикцию** — см. раздел 7.
- **Файловое хранилище**: S3-совместимое хранилище того же RU-провайдера.
  Пользовательские фото конвертируются в WebP. Фото, не попавшие ни в один
  заказ (брошенные формы), удаляет ежедневный cron
  (`/api/cron/cleanup-photos`, DEPLOY.md §4).
- **При масштабировании — не забыть** (решения, осознанно принятые под
  объём MVP и один инстанс приложения):
  - Очистку фото перевести с cron на **lifecycle-правило S3**: загрузки
    кладутся во временный префикс (например `pending/`), при создании
    заказа переносятся в постоянный, остальное хранилище удаляет само.
    Cron перебирает весь бакет и все заказы за раз и молча перестаёт
    работать, если сломается.
  - Лимит частоты загрузок (`lib/rate-limit.ts`) — в памяти процесса; при
    нескольких инстансах перенести в общее хранилище (Postgres/Redis).
- **Рендеринг страницы квеста**: `/q/[uuid]` — обычный динамический роут
  Next.js, рендерится **на лету при каждом заходе** из данных в Postgres
  (Server Component), а не пре-генерируется в статический файл при оплате.
  Причина: с PIN-защитой (см. ниже) серверный хоп при каждом просмотре
  неизбежен в любом случае, поэтому отдельный пайплайн
  "рендер-один-раз-в-S3" не даёт выигрыша на объёме MVP, только сложность.
  Фраза "статический HTML" из ТЗ трактуется как *результат* (самодостаточная
  страница без визуального конструктора), а не как буквальное требование
  единого файла. Пересмотреть, если/когда появится реальная нагрузка от
  вирального шеринга — тогда добавить кэширование (ISR/CDN) поверх этой же
  модели, не переписывая её с нуля.
- **Модерация фото (NSFW)**: **self-hosted NudeNet** (open-source, ONNX,
  ~7 МБ модель) как отдельный лёгкий сервис (FastAPI + Docker) на том же
  VPS, где крутится приложение — не платный SaaS (Sightengine/Cloudmersive).
  Причины: (а) при объёме MVP (~10 заказов/мес) платная подписка — это
  чистый фиксированный убыток ($29/мес и выше) без реальной необходимости;
  (б) self-hosted решение держит фото пользователей в RU-периметре, усиливая
  соответствие 152-ФЗ, вместо отправки на внешний западный API.
  Если объём вырастет настолько, что self-hosted решение перестанет
  справляться по качеству/скорости — тогда пересмотреть в пользу платного
  API, а не раньше.
- **Модерация текста**: OpenAI Moderation API (бесплатный) — без изменений
  от ТЗ.
- **Email-рассылки** (чек, PIN, напоминание об истечении ссылки,
  passwordless-вход в личный кабинет, реферальные коды): **UniSender** —
  выбран за репутацию доставляемости транзакционных писем через отдельную
  инфраструктуру (UniOne); объём писем на старте маленький, лимит
  бесплатного тарифа некритичен.

## 3. Тарифы и бизнес-модель

Две категории тарифов:

**База (основной поток дохода, линейная лестница — каждый следующий тариф
строго превосходит предыдущий):**

| Тариф | Цена | Шаблоны | Фото | Срок ссылки | PIN |
|---|---|---|---|---|---|
| Лёгкий | 199₽ | 2 без-фото шаблона («Выбери свидание», «Ты против меня») | 0 | 7 дней | нет |
| Квест | 499₽ | все 5 | до 10 | 1 год | нет |
| Максимум | 999₽ | все 5 | до 20 | 3 года, поддомен вида `slug.loveitseasy.ru` | да |

Тариф "Лёгкий" намеренно без фото — это не только ценовая сегментация, а
прямая экономия: без загрузки фото NSFW-модерация для этого тарифа не
задействуется вообще, только бесплатный текстовый модератор.

**Вторичные форматы (отдельная категория, не часть линейной лестницы —
на странице тарифов визуально отделены от "Базы", не конкурируют с ней по
принципу "лучше/хуже"):**

| Формат | Цена | Особенность | Фото |
|---|---|---|---|
| Для двоих | 799₽ | 2 страницы (взаимный обмен сюрпризами) | до 5 фото на страницу (10 всего) |

Список вторичных форматов открыт для расширения — новые "похожие" форматы
обсуждаются и добавляются в эту таблицу по мере проработки, не создаются
агентом самостоятельно.

**Домен**: только поддомен вида `<slug>.loveitseasy.ru`, **не** отдельный
платный домен — осознанное решение: (а) не тянет постоянные расходы на
регистрацию/продление домена на 3 года вперёд, (б) каждая расшаренная
ссылка несёт бренд в самом URL, что работает на органический маркетинг
(UGC-стратегия, раздел 7 ТЗ).

## 3a. Шаблоны

5 шаблонов из ТЗ, с одной переименованной/обобщённой позицией:

- «Ты самая красивая», «Выбери свидание», «Признание в любви»,
  «Ты против меня» (Квиз) — без изменений от ТЗ.
- «100 дней отношений» → **переименован в «Наша история»**: вместо жёстко
  зашитой даты "100-й день" пользователь вводит свою дату начала
  отношений (или любую важную дату), шаблон сам считает "X дней/месяцев/лет
  вместе" и строит таймлайн + YouTube-видео. Покрывает любую годовщину, а
  не один конкретный момент — не новый шаблон, а обобщение уже
  запланированного.

Кандидаты на новые шаблоны следующей волной (после MVP) — в `BACKLOG.md`.

## 4. Ключевые архитектурные и процессные решения

- **Модерация — до оплаты, а не после.** Кнопка оплаты активна только
  после того, как все загруженные фото и тексты прошли автоматическую
  проверку. Это устраняет конфликт между "без возврата после успешной
  генерации" (ТЗ) и законом о защите прав потребителей: раз контент уже
  прошёл модерацию к моменту оплаты, отказ доставки по вине контента не
  возникает как сценарий вообще.
  - Исключение, где возврат обязателен несмотря на общую политику:
    техническая ошибка генерации после оплаты (баг, битый файл и т.п.) —
    это "услуга не оказана", возврат тут не обсуждается.
  - Если человек, изображённый на фото, требует удаления уже после
    доставки (см. согласие ниже) — сервис был оказан корректно на момент
    покупки, возврат не обязателен, но вместо отказа предлагать бесплатную
    замену фото и перегенерацию ссылки.
- **PIN-защита ссылки** — обязательна для тарифа "Максимум" (и любых
  будущих тарифов с длительным хранением/чувствительным контентом).
  4-значный PIN, проверяется **на сервере** до отдачи данных квеста
  (не декоративная клиентская проверка — контент не должен присутствовать
  в HTML/JS до успешной проверки PIN).
- **Согласие на фото третьих лиц.** Перед загрузкой — обязательный чекбокс
  ("подтверждаю, что имею право использовать материалы и несу
  ответственность за согласие изображённых лиц"), без него загрузка
  недоступна. Факт согласия (с таймстампом) логируется в БД. Плюс — простая
  форма/e-mail для запроса удаления от человека, изображённого на фото
  (аналог takedown-процедуры), с оперативной обработкой.

## 5. Структура репозитория

Инициализировано `create-next-app` (Next.js 16.3.5, App Router, TypeScript
strict, Tailwind CSS v4, ESLint + Prettier). Фактическая раскладка:

```
/app                 — Next.js App Router (витрина, чекаут, /q/[uuid] — квест)
/public              — статика (иконки, favicon)
/templates           — шаблоны квестов, каждый как отдельный модуль/компонент (пусто, Фаза 8)
/lib/moderation      — клиент к self-hosted NudeNet-сервису + OpenAI Moderation (пусто, Фаза 6)
/services/nsfw       — self-hosted NudeNet (FastAPI + Docker), отдельный процесс (пусто, Фаза 2)
/lib/payments        — обёртка над платёжным провайдером (пусто, Фаза 7)
/lib/storage         — работа с S3-хранилищем и WebP-конвертацией (пусто, Фаза 5)
/lib/db              — доступ к PostgreSQL (миграции, схема) (пусто, Фаза 3)
/lib/access          — проверка PIN-кода для защищённых ссылок (пусто, Фаза 9)
```

Директории `/templates` и `/lib/*`/`/services/nsfw` пока содержат только
`.gitkeep` — наполняются по мере прохождения фаз `TODO.md`.

## 6. Конвенции кода

- TypeScript strict mode везде, без `any` без явной причины в комментарии.
- Компоненты — функциональные, без классов.
- Каждый шаблон квеста — самодостаточный модуль в `/templates/<name>`, не
  шарит состояние с другими шаблонами напрямую.
- Все тексты интерфейса — на русском (основная аудитория RU, 18–30 лет).
- Mobile First: любой новый UI-компонент сначала проверяется на узком вьюпорте.
- Лимиты тарифов (шаблоны/фото/срок/PIN, раздел 3) — единая конфигурация
  (например `lib/tariffs.ts`), не хардкодить цифры по месту в разных файлах.

## 7. Жёсткие границы — НЕ менять без явного запроса пользователя

Эти решения — часть бизнес- и юридической модели продукта, а не техническая
деталь. Агент не должен менять их «по инициативе» ради удобства реализации:

- **Не переносить хранение персональных данных/фото за пределы RU-провайдеров**
  (требование 152-ФЗ). Никаких сторонних западных SaaS для хранения PII.
- **Не заменять self-hosted NudeNet на платный внешний SaaS** без обсуждения
  — это одновременно вопрос юнит-экономики и данных, покидающих RU-периметр.
- **Не убирать и не обходить премодерацию** (NSFW-скан фото, toxicity-скан
  текста), и **не переносить её после оплаты** — оба момента защищают и от
  блокировок домена, и от конфликта с законом о защите прав потребителей.
- **Не менять модель монетизации на подписочную** — ТЗ явно фиксирует
  pay-per-use и отказ от подписок как защиту юнит-экономики.
- **Не индексировать страницы квестов** — обязательный `noindex` /
  запрет краулинга на всех `/q/[uuid]` страницах.
- **Не убирать PIN-проверку с сервера** для тарифов, где она включена —
  проверка обязана быть серверной, не косметической.
- **Не покупать отдельные платные домены на заказ** — только поддомен
  `*.loveitseasy.ru`.
- **Shareable Demo не должна содержать реальные фото/имена** пользователя —
  только размытые/заменённые данные, при этом анимация и логика сохраняются.
- **Не убирать чекбокс согласия на фото третьих лиц** и не убирать
  логирование факта согласия.

## 8. Открытые вопросы

Ещё не решено — не додумывать самостоятельно, поднимать с пользователем при
первом столкновении:

1. Выбор платёжного провайдера — Robokassa vs ЮKassa. Юридический статус
   уже решён (самозанятый/НПД), обе площадки работают с самозанятыми без
   расчётного счёта. Ориентир — Robokassa за автоматическое формирование
   чеков СМЗ в ФНС, но окончательный выбор ещё не сделан. Независимо от
   выбора — СБП как способ оплаты по умолчанию (комиссия 0-0,7% против
   ~2,6-3,5% у карт), карта — запасной вариант.
2. Точные пороги/threshold для NudeNet (баланс ложных срабатываний —
   слишком строгий порог режет нормальный контент до оплаты, слишком мягкий
   пропускает то, что должен ловить). Не решается заранее — прогнать
   тестовую пачку фото на этапе реализации модерации и подобрать порог там.
3. Каталог будущих "вторичных форматов" (по аналогии с "Для двоих") — пока
   существует только один, список открыт для расширения по мере обсуждения.

Продуктовые идеи вне текущего MVP (новые тарифы, фичи квеста, виральность,
retention) — в отдельном файле `BACKLOG.md`, не здесь.

## 9. Как запускать/тестировать

- `npm run dev` — локальный сервер разработки (Turbopack).
- `npm run build` / `npm run start` — production-сборка и запуск.
  Перед production-деплоем — обязательный чеклист `DEPLOY.md`.
- `npm run lint` — ESLint.
- `npm run format` — Prettier (автоформатирование всего проекта).
- Тесты — не настроены, фреймворк не выбран (появится, когда в проекте
  будет что тестировать помимо каркаса).
